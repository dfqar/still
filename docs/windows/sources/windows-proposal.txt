Да. Для Windows-версии **Still** я бы уже зафиксировал довольно конкретную архитектуру: **WinUI 3/.NET 10 как нативная оболочка + Rust как движок + wgpu/DX12 как renderer + `SwapChainPanel` как место, куда Rust рисует**.

Причём это не компромиссный костыль: `SwapChainPanel` как раз предназначен для размещения DirectX-контента внутри XAML-интерфейса, а актуальный `wgpu` имеет отдельный DX12 `SurfaceTargetUnsafe::SwapChainPanel`. :chatgpt-content-reference{index="0"}

# 2. Кто за что отвечает

Ключевой принцип:

> **Windows знает, что такое окно. Rust не знает.  
> Rust знает, что такое сцена. Windows не знает.**

То есть WinUI не должен знать:

```text

```

А Rust не должен знать:

```text
SettingsFlyout

Window titlebar
AppWindow
WinUI Button
Windows Settings
```

Граница должна быть очень узкой.

```text
Still.Windows

WindowManager

RenderHost
SettingsViewModel

WindowsLifecycle
```

### Rust

```text
still-core
still-render
still-scenes

```

# 3. Самое важное — `SwapChainPanel`

В XAML я бы сделал примерно такую композицию:

```text
Grid
│
├── SwapChainPanel       ← Rust/wgpu рисует сюда
│
├── InteractionLayer     ← обработка pointer/touch
│
└── Overlay
    ├── Scene title
    ├── sliders
    ├── performance menu
    └── settings button
```

То есть не:

```text
WinUI
↓
картинка от Rust
```

а буквально:

```text
          XAML

        Settings
           │
           │
   ┌───────▼─────────┐
   │                 │
   │  SwapChainPanel │
   │                 │
   │    DX12 image   │
   │                 │
   └─────────────────┘
```

Microsoft прямо проектирует `SwapChainPanel` для DirectX-контента внутри XAML visual tree; поверх него можно располагать обычные XAML controls. :chatgpt-content-reference{index="3"}

А `wgpu` сейчас умеет:

```rust
SurfaceTargetUnsafe::SwapChainPanel(...)
```

то есть может сделать surface непосредственно из такого WinUI-контрола. `wgpu` при этом удерживает ссылку на panel на время жизни surface. :chatgpt-content-reference{index="4"}

Это сильно чище, чем создавать отдельный Win32 child HWND.

# 4. Почему именно DX12 на Windows

Здесь я бы **не пытался поддерживать Vulkan и DX12 одновременно**.

Windows-версия:

```text
wgpu
 ↓
DX12
```

macOS:

```text
wgpu
 ↓
Metal
```

Android/Linux:

```text
wgpu
 ↓
Vulkan
```

Сам `wgpu` остаётся общим API и поддерживает D3D12, Metal и Vulkan. :chatgpt-content-reference{index="5"}

Это значит, что Drift всё равно выглядит так:

```rust
renderer.render(scene);
```

а не:

```rust
if windows {
    dx12_render();
}

if mac {
    metal_render();
}
```

**DX12 вообще не должен проникать в код сцены.**

Windows-specific код нужен только примерно здесь:

```text
still-platform-windows
        ↓
create Windows surface
        ↓
wgpu::Surface
```

И всё.

# 5. FFI между C# и Rust

Вот тут я бы **не использовал UniFFI для Windows**.

UniFFI официально прежде всего ориентирован на Swift, Kotlin и Python; C# bindings остаются сторонним направлением. :chatgpt-content-reference{index="6"}

Для Windows лучше:

```text
C ABI
+
P/Invoke
```

При желании C# bindings автоматически генерировать через `csbindgen`, который именно для этого и существует: Rust `extern "C"` → C# P/Invoke. :chatgpt-content-reference{index="7"}

# 7. Где должен находиться render loop

Здесь есть два варианта.

Для **Still 0.1 я бы намеренно выбрал самый простой**:

```text
WinUI CompositionTarget.Rendering
                 ↓
          still_render_frame()
                 ↓
               Rust
                 ↓
               GPU
```

У WinUI есть специальный `CompositionTarget.Rendering`; Microsoft прямо указывает DirectX interop как один из сценариев его использования. :chatgpt-content-reference{index="9"}

Получается:

```text
UI thread
│
│ CompositionTarget.Rendering
│
├── calculate Δt
│
└── Rust render_frame(dt)
          │
          ├── update scene
          ├── compute pass
          ├── render pass
          └── present
```

### Почему не отдельный render thread сразу

Потому что для Drift:

- simulation идёт преимущественно на GPU;
- CPU работы мало;
- 10–30k particles — вообще небольшая задача;
- XAML UI минимальный.

Отдельный render thread сразу принесёт больше проблем с:

- resize;
- lifetime;
- synchronization;
- SwapChainPanel;
- surface reconfiguration;
- shutdown;
- device lost.

И практически ничего не даст.

---

## Но архитектуру готовим под отдельный render thread

Позже:

```text
UI thread                    Render thread

Pointer ─────┐
Resize ──────┤
Settings ────┤
             ↓
        CommandQueue ──────────────► Engine
                                      │
                                      ↓
                                  Simulation
                                      ↓
                                     GPU
```

Важно, что даже если мы сначала рендерим через UI callback, **Engine API уже не зависит от этого решения**.

---

# 8. Почему `CompositionTarget.Rendering` нельзя оставлять работать постоянно

Потому что обработчик запускается каждый кадр на UI thread и заставляет UI-thread постоянно работать, что увеличивает энергопотребление. Microsoft прямо предупреждает об этом. :chatgpt-content-reference{index="10"}

Поэтому:

```text
Window visible
→ Rendering subscribed

Window minimized
→ Rendering unsubscribed

Window hidden
→ Rendering unsubscribed

Monitor off / suspend
→ renderer suspended

Window active again
→ Rendering subscribed
```

Для Still это особенно важно — иначе красивый ambient app будет бессмысленно жрать батарею.

# 9. Drift на Windows

Для первой сцены я бы **сразу делал GPU simulation**.

Не так:

```text
C# calculates particles
↓
Rust
↓
GPU
```

и даже не:

```text
Rust CPU calculates 30k particles
↓
uploads 30k particles every frame
↓
GPU
```

А:

```text
         GPU

ParticleBuffer A
       │
       ▼
Compute shader
       │
       ▼
ParticleBuffer B
       │
       ▼
Render pipeline
       │
       ▼
screen
```

Например частица:

```rust
struct Particle {
    position: vec2<f32>,
    velocity: vec2<f32>,
    age: f32,
    seed: f32,
}
```

примерно 24–32 байта после alignment.

Для 30 000 частиц:

```text
~1 MB
```

то есть совершенно ничтожный объём для современной GPU.

Даже 100–500 тыс. позже вполне реалистичны.

# 10. Frame pipeline

Каждый кадр:

```text
CompositionTarget.Rendering
             │
             ▼
         render(dt)
             │
             ▼
┌─────────────────────────┐
│ update FrameUniforms    │
│                         │
│ time                    │
│ delta                   │
│ pointer                 │
│ viewport                │
│ density                 │
│ flow                    │
│ speed                   │
└───────────┬─────────────┘
            ↓
      Compute Pass
            ↓
   update particles
            ↓
      Render Pass
            ↓
    particle trails
            ↓
     Post Processing
            ↓
        Present
```

CPU каждый кадр передаёт буквально несколько десятков/сотен байт uniform data.

# 11. Pointer interaction

WinUI ловит:

```text

PointerReleased
PointerWheelChanged
```

и переводит всё в **универсальную модель Still**:

```rust
InputEvent {
    pointer: Vec2,
```

```text

           \
iPhone touch ──► Still Input
           /

```

# 12. Pointer не двигает частицы напрямую

Лучше:

```text
mouse
 ↓
attractor / force field
 ↓
compute shader
 ↓
particle acceleration
```

Например:

\[
F = \frac{k}{r^2 + \epsilon}
\]

но с плавным falloff:

```text
pointer
   ●

      → ·
    → ·
  → ·

       · →→→
```

Можно сделать несколько режимов:

```text
Attract
Repel
Distort
Vortex
```

Но UI пользователю необязательно это показывать сразу.

# 13. Vector field

Для Drift:

```text
position
   ↓
noise(position × scale + time)
   ↓
angle
   ↓
direction
```

Пример:

\[
\theta =
noise(x \cdot s,\ y \cdot s,\ t) \cdot 2\pi
\]

\[
v =
(\cos \theta,\sin \theta)
\]

И:

\[
p_{t+1}=p_t + v\Delta t
\]

Можно делать multi-octave noise/fBm:

\[
N(p)=
N(p)
+0.5N(2p)
+0.25N(4p)
+...
\]

Это всё WGSL compute shader.

# 14. Trails

Это один из моментов, который решит, выглядит Still красиво или как школьный particle simulator.

Не очищаем framebuffer полностью.

Делаем:

```text
previous frame
      ↓
slight fade
      ↓
new particles
      ↓
new frame
```

Например:

```text
Frame N
   ↓
offscreen texture A
   ↓
fade shader
   ↓
texture B
   ↓
draw particles
   ↓
postprocess
```

Следующий кадр меняем A/B местами.

Это обычный ping-pong:

```text
Frame 1
A → B

Frame 2
B → A

Frame 3
A → B
```

Так получаются красивые шлейфы.

# 16. Resize и DPI

Windows здесь важен из-за scaling.

XAML работает в effective pixels/DIPs, а GPU нужен физический размер framebuffer.

Условно:

```text
SwapChainPanel
1280 × 720 DIP

scale = 1.5

Surface
1920 × 1080 px
```

Поэтому Windows shell передаёт движку:

```text
logicalWidth
logicalHeight
scaleFactor
physicalWidth
physicalHeight
```

При resize:

```text
SwapChainPanel.SizeChanged
         ↓
calculate physical size
         ↓
still_resize()
         ↓
Surface.configure()
         ↓
scene.resize()
```

Те же различия DPI/physical pixels присутствуют и при обычной работе WinUI с HWND; документация Microsoft отдельно обращает внимание на разницу effective и physical pixels. :chatgpt-content-reference{index="11"}

# 17. Surface configuration

Для начала я бы брал примерно такую философию:

```text
format:
preferred sRGB

present:
vsync

maximum frames in flight:
2

HDR:
off

probably off initially
```

`wgpu` поддерживает несколько present modes, включая синхронизированные и immediate/mailbox варианты. :chatgpt-content-reference{index="12"}

Но для Still:

**VSync важнее минимальной latency.**

Это не соревновательная игра.

Нам нужны:

```text

```

```text

```

# 18. 60 / 120 Гц

Не надо в коде делать:

```text
sleep(16.666 ms)
```

или тем более:

```text
fixed 60 fps
```

Simulation должна использовать:

```text
delta_time
```

Тогда:

```text
60 Hz
dt ≈ 16.7 ms

120 Hz
dt ≈ 8.3 ms

144 Hz
dt ≈ 6.9 ms
```

сцена физически движется с одинаковой скоростью.

А frame pacing предоставляет compositor/presentation layer.

`RenderingEventArgs.RenderingTime` у WinUI можно использовать для измерений времени рендера. :chatgpt-content-reference{index="13"}

# 19. Очень важный момент — fixed simulation time

Некоторые части scene simulation лучше не полностью привязывать к нестабильному `dt`.

Например:

```text
rendering:
variable timestep

physics:
fixed timestep
```

Допустим:

```text
simulation step = 1 / 120 s
```

Если пришло:

```text
dt = 16.6 ms
```

делаем два шага.

Если:

```text
dt = 8.3 ms
```

один.

Это даст одинаковое поведение Drift при разных refresh rates.

Но для первой простейшей procedural сцены variable dt тоже приемлем.

# 20. Device lost / surface lost

Это сразу стоит архитектурно предусмотреть.

Состояния renderer:

```text
Uninitialized
     ↓
Initializing
     ↓
Running
     ↓
Suspended
     ↓
Recovering
     ↓
Running
```

А не:

```text
wgpu error
→ panic
→ Still.exe умер
```

WinUI имеет `SurfaceContentsLost` именно для сценариев, где DirectX surface необходимо восстановить после серьёзного изменения underlying graphics state. :chatgpt-content-reference{index="14"}

Сам wgpu также возвращает состояния вроде:

```text
Outdated
Lost
Occluded
Timeout
```

при получении surface texture. :chatgpt-content-reference{index="15"}

Поэтому renderer:

```text
Lost
→ recreate/reconfigure surface

Outdated
→ resize/reconfigure

Occluded
→ skip frame

Timeout
→ skip + log
```

Итого runtime:

```text
Still.exe

still_engine.dll
Windows App SDK
...
```

Для начала я бы собирал только:

```text
win-x64
```

Потом:

```text
win-arm64
```

Никакой причины сразу поддерживать четыре Windows architecture нет.

# 25. Ошибки через FFI

Вот этого:

```rust
unwrap()
expect()
panic!()
```

на FFI boundary быть не должно.

Лучше:

```text
StillResult

OK
INVALID_HANDLE
GPU_INIT_FAILED
SURFACE_FAILED
DEVICE_LOST
INVALID_PARAMETER
INTERNAL_ERROR
```

И отдельно:

```text
still_get_last_error()
```

для текста.

То есть:

```text
Rust internal Result<T, E>
       ↓
FFI boundary
       ↓
StillResult
       ↓
C#
       ↓
log / recovery UI
```

# 29. Windows lifecycle

Для ambient-приложения это важнее, чем кажется.

```text
active + visible
→ full rendering

inactive but visible
→ optionally reduce FPS

minimized
→ stop rendering

occluded
→ stop/reduce

battery saver
→ optional lower quality

resume
→ restore timing

display changed
→ update DPI/HDR/surface
```

Это даст Still ощущение нормального приложения, а не GPU benchmark.

# 30. Fullscreen

Fullscreen тоже должен делать **Windows layer**, а не Rust.

Rust знает только:

```text
viewport = 3840 × 2160
```

Не знает:

```text
fullscreen = true
```

Windows через `AppWindow`/presenter управляет оконным режимом. WinUI `Window` и `AppWindow` оба работают поверх HWND-модели Windows. :chatgpt-content-reference{index="16"}

# 32. Что я бы зафиксировал прямо сейчас

Итоговая Windows-архитектура:

| Решение | Выбор |
|---|---|
| Language shell | C# |
| Runtime | .NET 10 LTS |
| UI | WinUI 3 |
| Windows SDK layer | Windows App SDK |
| Render host | `SwapChainPanel` |
| Core | Rust |
| GPU abstraction | wgpu |
| Windows backend | DX12 |
| Shaders | WGSL |
| FFI | C ABI + P/Invoke |
| C# bindings | csbindgen |
| Frame callback v0.1 | `CompositionTarget.Rendering` |
| Simulation | GPU compute |
| UI rendering | XAML |
| Scene rendering | wgpu |
| Persistence | native shell |
| Scene state | Rust |
| Windows target initially | x64 |

И я бы **не менял эту схему без конкретной проблемы**.

Главное преимущество в том, что Windows-специфичным получается совсем небольшой кусок:

```text
        Windows

WinUI ── SwapChainPanel
 │             │
 │             ▼
 │      create wgpu surface
 │
 └──── input / lifecycle
```

А всё интересное:

```text
Drift
Particles
Noise
Shaders
Trails
Postprocessing
Scene System
Parameter System
Modulation
```

уже является **Still**, а не **Still.Windows**.

Поэтому когда мы дойдём до macOS, архитектура должна превратиться примерно в `SwiftUI + Metal-backed wgpu surface → тот же Engine`, а не в переписывание проекта с нуля. Именно по этому признаку я бы и оценивал, хорошая у нас Windows-архитектура или нет.
